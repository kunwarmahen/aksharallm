– Stopping is safe at any step: the trainer saves ckpt_last.pt where it stopped and the next start resumes there with no loss spike. The explainer runs on your machine through Ollama and writes nothing. It shares the GPU with training — configs/portal.yaml keeps its context small and unloads the model a few minutes after you stop asking. Every job shells out to python -m aksharallm.quant — the same command you would type — and writes its measurements to logs/quant/. int8 is free; int4 costs perplexity and saves memory, not time. See docs/10 for why smaller is not faster. An adapter is a few MB, not a new copy of the model — one base plus one adapter per skill. Jobs shell out to python -m aksharallm.train.sft and write beside the base they came from, so the Playground picks them up. See docs/11 for why the rank and the target layers matter more than anything else here. A benchmark score means nothing on its own — read it against the chance line, the error bar, and what the same suite scored ten thousand steps ago. Data is downloaded once into data/eval/; results are kept forever in logs/eval/. See docs/12 for what each suite can and cannot tell you. Generated data is the easiest way to make a model worse while its loss improves, so read the funnel, not the sample count: which filter the rest of the batch hit is what says whether to change the prompt, the teacher or the seed grid. The python recipe runs the tests it wrote, then runs them again against a stubbed solution. Everything lands in data/synth/ with its provenance. See docs/13. The second paradigm in this repo, at 13.8M on TinyStories — never the main model, because masked diffusion needs roughly 3–16x the compute of next-token prediction for equal quality. Its validation loss is an ELBO upper bound and is not comparable with an autoregressive run's cross-entropy. What it buys is infilling and a compute dial. See docs/19. Every lesson ends in a real test: break the code the lesson names, watch that test go red, put it back. A lesson only counts as done once its check has gone red and then green — the check passes on a clean checkout, so breaking it is the exercise. Same lessons and the same progress file as python -m aksharallm.learn. See docs/15. Every generation is recorded in logs/playground.jsonl with the step and loss of the checkpoint that produced it, so the same prompt at step 7,000 and step 30,000 can be put side by side. While a run is training this loads on the CPU instead of the GPU.
